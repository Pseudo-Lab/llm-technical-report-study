# W12 — GLM-4.5: 본문 구성요소와 선행 개념

[W12 학습목표](../weeks/w12/README.md) · [전체 읽기 지도](README.md) · [읽기 분담](workload.md)

## 이번 주 읽기 범위

이 문서는 [GLM-4.5 v1](https://arxiv.org/abs/2508.06471v1)의 **본문에 실제로 등장하는** 구성요소를, W12의 세 목표 밖까지 포함해 정리한다. `채택`은 기존 기법을 보고서가 사용한 경우, `변경`은 기존 방법의 배치·학습법을 바꾼 경우, `제안`은 이 보고서가 자기 방법으로 설명한 경우다. 외부 원전이 없는 운용 규칙은 보고서 본문을 원전으로 둔다.

공통 읽기는 [주차별 분담표](workload.md)에 적힌 대상 본문으로 시작한다. 담당 심화에서는 아래 구성요소 중 한 갈래와 필요한 선행 원전의 지정 절을 읽는다.

## 본문 구성요소와 선행 개념

### 1. 기반 모델: sparse MoE, attention, 추론 초안

#### MoE routing과 깊이/폭 선택

- **본문 출발점:** [§2.1, Table 1](https://arxiv.org/abs/2508.06471v1). GLM-4.5는 3 dense + 89 MoE layer, token당 8개 routed expert와 1 shared expert를 쓰며, loss-free balance routing과 sigmoid gate를 채택한다.
- **작동과 필요:** router가 token마다 일부 expert만 활성화하므로 총 parameter를 키우되 token당 계산은 제한한다. 여기서 “loss-free”는 별도의 auxiliary balancing loss로 주 손실을 교란하지 않고 routing bias를 조정한다는 뜻이다. 보고서는 DeepSeek-V3·Kimi K2보다 폭(숨은 차원·routed expert 수)을 줄이고 층수를 늘려 reasoning에 유리했다고 주장한다.
- **원전 경로:** 보고서가 직접 인용한 [DeepSeek-V3 v2 §2.1.2](https://arxiv.org/abs/2412.19437v2)는 auxiliary-loss-free balance와 sigmoid gating의 원전이다. GLM-4.5의 “더 깊고 좁게”라는 선택 자체는 이 보고서의 §2.1이다.
- **경계:** loss-free balancing은 GLM-4.5가 새로 제안한 router가 아니라 **채택**이다. 깊이/폭 비율과 Table 1 구성은 이 모델의 **변경/선택**이다.
- **확인 질문:** total parameter와 activated parameter가 다른 이유는 무엇이며, 8 routed + 1 shared expert가 매 token에 모두 계산되는 expert 수를 어떻게 제한하는가?

#### GQA와 partial RoPE

- **본문 출발점:** [§2.1, Table 1](https://arxiv.org/abs/2508.06471v1). 96 query head와 8 KV head의 GQA 및 partial RoPE를 쓴다.
- **작동과 필요:** GQA는 여러 query head가 더 적은 KV head를 공유해 KV cache를 줄인다. partial RoPE는 위치 회전을 일부 channel에만 적용해 위치 회전과 content channel을 분리한다.
- **원전 경로:** GQA·partial RoPE의 정확한 GLM-4.5 배치와 head 수는 보고서가 별도 원전을 연결하지 않으므로 §2.1 자체를 1차 원전으로 읽는다. RoPE 기본식은 [W01 Llama 가이드](w01.md)로 되돌아간다.
- **경계:** 96/8 head 및 partial-RoPE 조합은 보고서의 **구성 선택**이다. partial RoPE의 별도 신규 수식은 제시하지 않는다.
- **확인 질문:** Q head 수를 96으로 늘려도 KV head가 8이면, cache의 어느 축과 attention score의 어느 축이 각각 달라지는가?

#### QK-Norm

- **본문 출발점:** [§2.1](https://arxiv.org/abs/2508.06471v1). QK-Norm으로 attention logit range를 안정화한다고 명시한다.
- **작동과 필요:** query와 key의 크기가 과도하게 커지면 내적 logit의 scale이 softmax를 포화시킬 수 있다. QK-Norm은 두 vector의 norm을 통제해 이 불안정을 줄이는 normalization이다.
- **원전 경로:** 보고서가 직접 인용한 [Query-Key Normalization for Transformers §2–§3](https://arxiv.org/abs/2010.04245)를 읽는다.
- **경계:** QK-Norm은 **채택**이며, GLM-4.5는 적용 위치나 별도 ablation을 공개하지 않는다.
- **확인 질문:** logit clipping과 QK normalization은 softmax 전에 각각 어떤 값을 직접 제한하는가?

#### MTP layer와 speculative decoding

- **본문 출발점:** [§2.1, Table 1](https://arxiv.org/abs/2508.06471v1). MoE MTP layer를 넣어 inference 시 speculative decoding을 지원한다.
- **작동과 필요:** MTP draft가 다음 여러 token 후보를 내면 큰 target model이 한 번에 검증해 accept한 만큼의 decoding step을 건너뛴다. 따라서 MTP는 모델 정확도 목표와 별개로 latency/throughput을 겨냥한 보조 head다.
- **원전 경로:** 직접 인용은 [Better & Faster LMs via MTP v1 §2·§3.2](https://arxiv.org/abs/2404.19737v1)다. speculative decoding은 본문에 이름이 나오지만 별도 원전 인용은 없으므로 [Speculative Decoding v2 §2–§3](https://arxiv.org/abs/2211.17192v2)를 **개념 원전 보충**으로 읽는다.
- **경계:** MTP와 speculative decoding은 **채택**이고, GLM-4.5는 MTP layer를 MoE로 둔 **구성 선택**만 밝힌다. accept length 결과는 이 보고서에 제시하지 않는다.
- **확인 질문:** draft token이 모두 accept되지 않아도 speculative decoding이 유용할 수 있는 이유를, target forward 호출 횟수로 설명할 수 있는가?

### 2. 데이터와 mid-training: 일반 corpus를 agent 문맥으로 바꾸는 단계

#### 품질 bucket과 semantic deduplication

- **본문 출발점:** [§2.2](https://arxiv.org/abs/2508.06471v1). 웹 문서를 quality bucket으로 나누고 high-quality bucket을 upsample하며, template 유사 문서는 embedding 기반 SemDedup으로 제거한다.
- **작동과 필요:** MinHash는 표면 문자열이 달라진 template page를 놓칠 수 있어 embedding 유사도로 중복을 제거한다. quality bucket은 quality score를 hard-delete만 하지 않고 sampling frequency로 바꾼다.
- **원전 경로:** 직접 인용한 [SemDeDup §2–§3](https://arxiv.org/abs/2303.09540v1), [Nemotron-CC §3–§4](https://arxiv.org/abs/2412.02595v1), [FineWeb2 §2–§4](https://arxiv.org/abs/2506.20920v1)를 순서대로 읽는다.
- **경계:** filter는 **채택**이다. bucket epoch 수와 교육성 score는 GLM-4.5의 **운용 선택**이다.
- **확인 질문:** MinHash로 제거 가능한 중복과 embedding-based SemDedup이 겨냥하는 중복은 어떤 입력 차이 때문에 갈리는가?

#### Fill-in-the-Middle (FIM)

- **본문 출발점:** [§2.2](https://arxiv.org/abs/2508.06471v1). source-code 전부에 FIM objective를 적용한다.
- **작동과 필요:** prefix와 suffix를 함께 주고 그 사이를 생성하게 만들어, 파일 끝에서만 이어 쓰는 next-token objective보다 code edit/infill 상황을 학습한다.
- **원전 경로:** 보고서가 직접 인용한 [Efficient Training of LMs to Fill in the Middle §2–§3](https://arxiv.org/abs/2207.14255v1)를 읽는다.
- **경계:** FIM은 **채택**이다. GLM-4.5는 exact FIM formatting/mixing ratio를 공개하지 않는다.
- **확인 질문:** suffix를 입력에 노출하면, pure left-to-right continuation에 없는 어떤 제약을 모델이 이용할 수 있는가?

#### repository-level code context

- **본문 출발점:** [§2.3, Figure 3](https://arxiv.org/abs/2508.06471v1). 4K 일반 pre-training 뒤 source file을 repository 단위로 묶고, issue–PR–commit association과 diff를 32K stage에 넣는다.
- **작동과 필요:** 파일 하나의 next-token loss에는 import, issue의 요구, 후속 PR의 patch가 서로 멀리 떨어져 있다. 이를 한 window에 놓으면 cross-file dependency와 issue→변경→commit 관계를 prediction context로 쓸 수 있다.
- **원전 경로:** file concatenation과 issue/PR/commit association의 정확한 순서는 GLM-4.5가 외부 방법으로 위임하지 않은 **§2.3 자체 원전**이다.
- **경계:** report는 repository sampling rule, file ordering, leakage 제거 방식을 공개하지 않는다. 따라서 “repo-level training”을 특정 공개 corpus나 code agent benchmark로 바꾸어 쓰지 않는다.
- **확인 질문:** issue와 diff를 같은 context에 둘 때 모델이 file-only code에서 얻을 수 없는 supervision은 무엇인가?

#### 합성 reasoning·agent trajectory와 context-length stage

- **본문 출발점:** [§2.3, Figure 3](https://arxiv.org/abs/2508.06471v1). 32K stage에 500B synthetic reasoning을, 128K stage에 long document와 100B synthetic agent trajectory를 추가한다.
- **작동과 필요:** 긴 문맥 창만 키워도 긴 reasoning path나 tool interaction의 분포가 없으면 장문 supervision을 받지 못한다. stage별 mixture는 context capacity와 그 창에서 수행할 task distribution을 함께 바꾸는 선택이다.
- **원전 경로:** 4K→32K→128K 순서, token 규모, trajectory mixture는 GLM-4.5 **자체 recipe**다.
- **경계:** report는 synthetic teacher, prompt, trajectory verifier, 각 source 비율을 공개하지 않는다. 따라서 여기서 별도의 synthetic-data 방법을 추정해 넣지 않는다.
- **확인 질문:** context length만 128K로 늘리는 것과 128K agent trajectory를 함께 넣는 것은 무엇이 다른가?

#### best-fit packing과 truncation

- **본문 출발점:** [§2.3](https://arxiv.org/abs/2508.06471v1). pre-training의 random truncation과 달리 mid-training에는 best-fit packing을 쓴다고 명시한다.
- **작동과 필요:** random cut은 짧은 일반 문서에서 위치 다양화를 주지만, 완결된 CoT·code block·tool trajectory를 자를 수 있다. packing은 boundary를 보존한 sequence들을 context window에 채워 token 낭비와 불완전 supervision을 함께 줄인다.
- **원전 경로:** 직접 인용한 [Fewer Truncations Improve LM §2–§4](https://arxiv.org/abs/2404.10830v1)를 읽는다. GLM-4.5의 phase별 선택은 §2.3이다.
- **경계:** report는 packing algorithm의 bin size·separator·attention mask를 명세하지 않는다. packing이 모든 pre-training data에서 random truncation보다 낫다고 일반화하지 않는다.
- **확인 질문:** pre-training에서는 random truncation을 data augmentation으로 허용하면서 mid-training에서는 packing으로 바꾸는 이유는 무엇인가?

#### Muon optimizer와 parameter 적용 범위

- **본문 출발점:** [§2.4](https://arxiv.org/abs/2508.06471v1). embedding, bias, RMSNorm을 제외한 parameter에 Muon을 적용하고, N=5, momentum=0.95, update RMS=0.2를 쓴다.
- **작동과 필요:** Muon은 2D hidden-weight update를 orthogonalization해 update의 singular value가 한 축에 몰리지 않게 조절하는 optimizer다. scalar/vector 성격의 embedding·bias·normalization parameter까지 같은 matrix update로 취급하지 않는 적용 분리가 보고서에 명시돼 있다.
- **원전 경로:** 직접 인용한 [Muon: An Optimizer for Hidden Layers](https://kellerjordan.github.io/posts/muon/)와 [Muon Is Scalable for LLM Training §2–§3](https://arxiv.org/abs/2502.16982v1)을 읽는다.
- **경계:** Muon은 **채택**이고 제외 parameter·N·momentum·RMS는 GLM-4.5의 **recipe**다. 제외 이유의 세부 이론은 본문이 제공하지 않으므로 추론과 사실을 구분한다.
- **확인 질문:** 왜 embedding/RMSNorm까지 동일한 matrix-orthogonalization update에 넣지 않았는지, 보고서가 실제로 명시한 범위와 추론을 구분해 말할 수 있는가?

#### sequence-length 전환과 RoPE base

- **본문 출발점:** [§2.4](https://arxiv.org/abs/2508.06471v1). 32K 전환 때 RoPE base를 10,000에서 1,000,000으로 바꾸고 cosine decay 및 batch-size warmup을 사용한다.
- **작동과 필요:** RoPE의 각 frequency는 position에 따른 회전각을 만든다. base를 바꾸면 긴 거리에서의 rotation spectrum이 달라지므로, 4K에서 학습한 위치 패턴을 더 긴 window로 옮길 때의 위치 encoding 설정을 함께 조절한다.
- **원전 경로:** RoPE 회전 정의는 [RoFormer §3.2](https://arxiv.org/abs/2104.09864v5)다. base 변경 시점·scheduler·batch schedule은 GLM-4.5 §2.4의 **운용 선택**이다.
- **경계:** 보고서는 RoPE base 하나의 ablation을 제시하지 않는다. 128K 결과를 base 변경만의 효과로 귀속하지 않는다.
- **확인 질문:** context 길이와 RoPE base는 각각 모델의 어떤 입력 범위와 position-frequency mapping을 바꾸는가?

### 3. 후학습: expert, reward, agent trajectory

#### expert→overall SFT와 hybrid thinking mode

- **본문 출발점:** [§3–§3.1](https://arxiv.org/abs/2508.06471v1). Reasoning·Agent·General expert를 cold-start SFT+domain RL로 만들고, expert output을 Overall SFT로 모아 explicit thought와 direct response를 모두 학습한다.
- **작동과 필요:** domain expert의 긴 CoT/agent trajectory를 하나의 base에 distill하되, 잡담처럼 빠른 응답이 필요한 sample에는 thought가 없는 response도 섞어 mode interference를 줄이려는 설계다.
- **원전 경로:** 이 expert separation과 overall SFT 순서는 외부 선행 논문으로 위임하지 않은 GLM-4.5의 **자체 본문 원전**이다. GRPO의 공통 골격만 [W07](../weeks/w07/README.md)에서 재사용한다.
- **경계:** “능력 통합”과 hybrid mode는 **제안된 training recipe**이며, 어떤 expert가 어떤 비율로 기여했는지 ablation은 제시되지 않는다.
- **확인 질문:** expert output을 같은 student가 재학습하는 것과 expert parameter를 병합하는 것은 어떤 점에서 다른가?

#### reasoning RL의 reward-variance curriculum

- **본문 출발점:** [§3.2, Figures 5–7](https://arxiv.org/abs/2508.06471v1). pass@8=0와 pass@512>0을 기준으로 hard prompt를 골라 two-stage curriculum을 만들고 64K single-stage RL, dynamic temperature를 쓴다.
- **작동과 필요:** GRPO는 같은 prompt rollout group의 상대 reward로 advantage를 만든다. 전부 실패하거나 전부 성공하면 group 안의 비교 신호가 약해지므로, correct/incorrect path가 함께 나올 난도를 의도적으로 고른다. 64K는 긴 CoT가 training sequence에서 잘리지 않게 하는 선택이다.
- **원전 경로:** GRPO 공통식은 직접 인용한 [DeepSeekMath v3 §4.1.1–§4.1.3](https://arxiv.org/abs/2402.03300v3)이다. prompt threshold, length/temperature schedule은 GLM-4.5 §3.2의 **자체 운용**이다.
- **경계:** Figures 5–7은 GLM-4.5 본체가 아닌 작은 실험 모델 결과다. report는 pass@8/pass@512가 모든 domain의 최적 난도 selector라는 보편 주장을 하지 않는다.
- **확인 질문:** reward variance가 0인 group과 correct/incorrect rollout이 공존하는 group은 GRPO advantage에서 어떤 차이가 나는가?

#### code RL의 token-weighted loss

- **본문 출발점:** [§3.2.3](https://arxiv.org/abs/2508.06471v1). code RL에서 sequence별 평균 대신 token-weighted mean으로 loss를 집계한다고 설명한다. importance sampling의 policy-ratio correction과 구별한다.
- **작동과 필요:** sequence별 mean을 먼저 내면 짧은 trace와 긴 trace가 같은 sample weight를 받는다. token-weighted mean은 실제 생성 token 수에 비례해 aggregation해 긴 code trajectory의 gradient 기여를 다르게 만든다.
- **원전 경로:** GRPO의 group-relative objective는 [DeepSeekMath v3 §4.1.1–§4.1.3](https://arxiv.org/abs/2402.03300v3), token weighting의 적용은 GLM-4.5 §3.2.3 **자체 원전**이다.
- **경계:** 본문은 token weighting의 exact formula와 broad code benchmark ablation을 공개하지 않는다. 따라서 긴 output이 항상 더 좋은 target이라는 뜻으로 읽지 않는다.
- **확인 질문:** token-weighted mean과 sequence-mean이 긴/짧은 trace에 주는 가중치를 어떻게 다르게 만드는가?

#### agent RL의 outcome·format reward

- **본문 출발점:** [§3.3](https://arxiv.org/abs/2508.06471v1). search와 SWE에서 final outcome reward, format penalty, model-generated token-only loss를 사용한다.
- **작동과 필요:** environment observation은 action의 결과를 설명하는 context지만 policy가 생성한 action token은 아니다. tool protocol을 어긴 trace를 0점 처리하면 final answer가 우연히 맞더라도 invalid action path를 강화하지 않는다.
- **원전 경로:** outcome/format 분리, token mask, search/SWE rollout은 GLM-4.5 §3.3의 **자체 원전**이다.
- **경계:** report는 format penalty의 수치와 모든 tool schema의 reward design을 공개하지 않는다. terminal state pass가 open-ended answer quality 전체를 대체하지 않는다.
- **확인 질문:** environment feedback을 context에 넣되 loss mask에서 빼야 하는 이유는 무엇인가?

#### general RL의 constraint taxonomy와 feedback source

- **본문 출발점:** [§3.4, Figures 8–9](https://arxiv.org/abs/2508.06471v1). 7 major/151 minor constraint type을 정하고 deterministic rule, human preference, AI feedback을 결합한다.
- **작동과 필요:** word count·format·keyword처럼 실행 가능한 조건은 rule verifier로, helpfulness·coherence처럼 열린 품질은 human/RM/critique로 평가한다. 같은 “instruction following” reward에 합쳐도 관측 가능한 failure 종류는 다르다.
- **원전 경로:** taxonomy·feedback mixture·function-call stepwise/end-to-end split은 GLM-4.5 §3.4의 **자체 원전**이다.
- **경계:** 151개 taxonomy가 공개 표준 ontology라는 뜻은 아니다. report는 rule/RM/AI feedback의 비율이나 오류율을 공개하지 않는다.
- **확인 질문:** deterministic checker가 통과한 응답도 human preference에서 낮은 점수를 받을 수 있는 instruction 예는 무엇인가?

#### XML-like function-call serialization

- **본문 출발점:** [§3.1, Figure 4](https://arxiv.org/abs/2508.06471v1). code-containing argument의 character escaping을 줄이기 위해 XML-like special tag template을 쓴다.
- **작동과 필요:** JSON string 안 code는 quote와 backslash를 다시 escape해야 한다. value를 tag 사이의 native text로 표현하면 action serialization sequence의 quoting burden이 줄고, tool parser가 action boundary를 더 명확히 읽을 수 있다.
- **원전 경로:** 이 template은 GLM-4.5 §3.1의 **자체 원전**이다.
- **경계:** XML-like text가 JSON보다 일반적으로 더 정확하다는 ablation은 본문에 없다. report가 공개한 것은 이 모델의 function-call template 선택이다.
- **확인 질문:** 동일한 Python string argument를 JSON string과 XML-like text로 직렬화할 때 필요한 escape token은 어떻게 달라지는가?

#### agent SFT의 tool→task→trajectory→filter 단계

- **본문 출발점:** [§3.1, Figure 4](https://arxiv.org/abs/2508.06471v1). tool/API collection, task synthesis, trajectory generation, quality filtering의 네 단계를 제시한다.
- **작동과 필요:** tool 명세를 모은 뒤 task를 만들고 user simulator와 model이 action trajectory를 생성한다. objective answer verification, subjective RM, terminal-state check는 각각 정답·응답 품질·환경 완료 실패를 걸러 SFT target을 선별한다.
- **원전 경로:** 네 단계와 filter 조합은 GLM-4.5 §3.1의 **자체 원전**이다.
- **경계:** report는 tool collection의 license/source, simulator prompt, filter threshold를 공개하지 않는다. filter 통과가 real-world tool success 보증은 아니다.
- **확인 질문:** trajectory filter에서 objective answer verification, subjective RM, terminal-state check가 서로 다른 실패를 잡는 이유는 무엇인가?

#### Slime train·rollout·data-buffer infrastructure

- **본문 출발점:** [§3.5, Figure 10](https://arxiv.org/abs/2508.06471v1). train, rollout, data buffer의 세 모듈과 synchronous/async mode 및 HTTP endpoint를 설명한다.
- **작동과 필요:** rollout worker가 task environment에서 trajectory를 만들고 central buffer가 learner와 전달을 분리한다. sync co-location은 model weight freshness를, async decoupling은 long rollout의 hardware utilization을 우선하는 서로 다른 scheduling choice다.
- **원전 경로:** GLM-4.5가 설명한 interface와 deployment mode는 §3.5 **자체 원전**이다. public framework 구현은 [THUDM/slime](https://github.com/THUDM/slime)에서 별도 확인할 수 있지만, report가 그 repository의 모든 구현을 명세하지는 않는다.
- **경계:** Figure 10은 infra topology이지 policy quality 비교가 아니다. HTTP/data buffer만으로 agent success가 생긴다는 인과는 제시하지 않는다.
- **확인 질문:** synchronous co-location과 asynchronous decoupling은 각각 weight freshness와 device utilization 중 무엇을 우선하는가?
