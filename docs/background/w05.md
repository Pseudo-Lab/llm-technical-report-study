# W05 — DeepSeek-V3: MoE 목표·data interface·FP8 시스템·후학습

[W05 학습목표](../weeks/w05/README.md) · [W04 DeepSeek-V2 가이드](w04.md) · [전체 읽기 지도](README.md)

DeepSeek-V3 [§2–§5와 Appendix B–C](https://arxiv.org/abs/2412.19437v2)는 V2의 MLA/DeepSeekMoE를 유지한 채, routing objective, multi-token objective, data/tokenizer interface, distributed system, FP8 numerical design, R1 distillation과 RL을 바꾼다. 따라서 W05의 세 목표만 읽고 나면 “V3는 FP8 MoE”라는 표어만 남는다. 아래는 보고서 본문이 실제로 전제하는 구성요소를 따른 읽기 경로다.

## 5. V3가 한 문장으로 나열한 구성요소를 분해하기

### 5.1 document packing과 attention mask

두 sample을 하나의 4K sequence에 붙인 메모를 만든다. padding/truncation 감소는 packing의 효과이고, sample 경계를 mask로 막을지는 별도 interface 선택이다. V3는 후자를 쓰지 않는다. 원전 범위와 V3의 선택은 위 §2 표에 있다.

### 5.2 FIM은 특별한 token 순서의 language modeling이다

PSM의 token 순서만 적는다: `<fim_begin> prefix <fim_hole> suffix <fim_end> middle <eos>`. middle을 마지막에 두어 causal LM이 prefix/suffix 뒤에 middle을 예측하게 하며, 이는 DPO/SFT가 아닌 base-model data transform이다.

### 5.3 BBPE pretokenizer와 boundary bias

예를 들어 마지막 `\n`이 없는 few-shot prompt는 punctuation+line-break fused token의 경계를 만나지 않아, 같은 내용이라도 마지막 tokenization이 달라질 수 있다. V3는 학습 중 일부 fused token을 random split해 이 case를 노출한다.

### 5.4 PP·EP·DP와 DualPipe

한 줄씩 분리한다: PP는 layer stage, EP는 routed-expert placement, DP/ZeRO는 data replica/optimizer state, DualPipe는 이 연산들을 겹치는 schedule이다. 따라서 `EP64`를 DualPipe의 수치라고 쓰지 않는다.

### 5.5 dispatch/combine all-to-all

`dispatch: token hidden state → selected expert`, `combine: expert output → original token owner`로 화살표를 그린다. direction과 tensor shape가 반대이므로 MTP state transfer와 같은 communication으로 부르면 안 된다.

### 5.6 recomputation, EMA, MTP parameter sharing

세 줄 메모: recomputation은 backward에 다시 계산해 activation 저장을 줄이고, EMA는 CPU에 비동기 보관하며, MTP/main head sharing은 duplicate parameter/gradient를 없앤다. V3의 자체 system setting과 해당 절의 근거는 위 §3 표에 있다.

### 5.7 FP8: format, scale, accumulation, state

표의 네 열(format, scale group, accumulation, optimizer/storage)을 직접 만들어 V3 수치를 각각 한 칸에 넣는다. 특히 input이 FP8이어도 sum이 FP8이라는 뜻은 아니며, Appendix B.2의 Dgrad divergence는 scale group을 임의로 바꿀 수 없다는 반례다.

### 5.8 prefill·decode는 같은 MoE의 다른 deployment이다

V3의 자체 deployment 설정은 prefill `TP4+SP, DP8, EP32`와 decode `TP4+SP, DP80, EP320`으로 다르다. TP는 attention linear operation, SP는 sequence slice, DP/EP는 replica/expert placement를 나눈다. redundant-expert policy와 IB direct point-to-point는 §3.4 자체를 1차 근거로 읽는다.

또한 [§3.4.1](https://arxiv.org/abs/2412.19437v2)은 prefill에서 한 micro-batch의 attention/MoE와 다른 micro-batch의 dispatch/combine·TP communication을 overlap하고, [§3.4.2](https://arxiv.org/abs/2412.19437v2)은 decode에서 attention과 다른 micro-batch의 dispatch+MoE+combine을 겹친다고 한다. decode의 expert batch는 보통 256 token 이내이고 memory access가 bottleneck이므로, training의 DualPipe를 그대로 serving에 적용한 것이 아니다. **작은 점검:** prefill `EP32`와 decode `EP320` 중 어느 쪽이 expert당 batch를 크게 만들며, 어느 쪽이 low-latency direct transfer를 택하는지 본문 수치와 함께 설명한다.

### 5.9 hardware co-design 제안은 현재 V3 구현과 구분한다

[V3 §3.5.1–§3.5.2](https://arxiv.org/abs/2412.19437v2)은 model layer가 아니라 향후 hardware 제안을 적는다. communication은 SM이 IB↔NVLink forwarding, RDMA-buffer transfer, combine reduction, chunk layout을 맡는 비용을 지적하고, scale-out/scale-up network를 하나의 read/write/multicast/reduce interface로 보이게 할 co-processor를 제안한다. 이때 직접 인용한 [SHArP (Graham et al., 2016) 공식 PDF §I–III](https://network.nvidia.com/pdf/solutions/hpc/paperieee_copyright.pdf)의 in-network reduction 배경과, [NVIDIA GPUDirect Async 자료](https://developer.nvidia.com/blog/improving-network-performance-of-hpc-systems-using-nvidia-magnum-io-nvshmem-and-gpudirect-async)의 current async communication context를 함께 읽는다.

compute 쪽에서는 FP8 accumulator precision, tile/block scale을 Tensor Core에서 받는 지원, online cast와 TMA access의 fusion, forward 1×128 tile을 backward 128×1로 읽는 transposed GEMM support를 제안한다. 이는 V3가 이미 채택한 FP8 recipe의 **제약에서 도출한 vendor recommendation**이며, 현재 H800에서 이미 제공된 model feature라고 쓰면 안 된다. **작은 점검:** “V3 runtime implementation”과 “future chip request”를 두 열로 나누고, 각 항목을 어느 열에 둘지 쓴다.
