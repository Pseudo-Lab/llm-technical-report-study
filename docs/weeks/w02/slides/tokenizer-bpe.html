모델은 글자가 아니라 숫자만 계산합니다. 문장을 어떻게 숫자로 바꿀지가 첫 질문입니다. Llama 2 논문은 이걸 “LLaMA 1과 같은 tokenizer를 쓴다” 한 줄로 넘깁니다. 그 한 줄 뒤에 무엇이 있는지 풀어 보겠습니다. (1분)

subword를 만드는 방법은 세 가지입니다. 오늘은 LLaMA가 쓴 BPE를 깊게 봅니다. 한 가지 구분: SentencePiece는 알고리즘이 아니라 BPE나 Unigram을 돌리는 라이브러리입니다. LLaMA는 SentencePiece 위에서 BPE를 씁니다. 단어 앞에 붙는 ▁ 표시는 SentencePiece의 규칙입니다. 공백 위치를 표시로 남기는 생각 자체는 2012년 WordPiece 논문에도 있었습니다(밑줄 표시). BERT의 WordPiece 구현은 반대로 이어지는 조각에 ##을 붙입니다. (1.5분)

BPE 학습: 가장 자주 붙는 쌍을
합치고, 그 순서를 기록합니다

① 단어를 글자로 쪼갠다 → ② 인접 쌍의 빈도를 단어 빈도만큼 더해 센다 → ③ 가장 많은 쌍을 새 토큰으로 합친다 → ④ 정한 어휘 크기까지 반복.

학습의 결과물은 어휘와 병합 규칙의 순서입니다.

초기 말뭉치low ×5 lower ×2 newest ×6 widest ×3
규칙병합빈도 계산병합 후 바뀐 단어
1e + s → esnewest 6 + widest 3 = 9newest widest
2es + t → est6 + 3 = 9newest widest
3l + o → lolow 5 + lower 2 = 7low lower
4lo + w → low5 + 2 = 7low lower

동점: 1단계 e+s = s+t = 9, 3단계 l+o = o+w = 7 → 먼저 센 쌍을 고르는 구현 규칙으로 결정
Python Counter.most_common과 Node 재구현에서 같은 순서 확인 · 알고리즘: Sennrich 2016 Algorithm 1

근거: Sennrich et al. 2016 · §3.2 · Algorithm 1
글자로 쪼개고, 가장 자주 붙는 쌍을 합쳐 새 토큰으로 어휘에 넣고, 다시 세서 반복합니다. 정한 어휘 크기, LLaMA는 32,000개가 될 때까지 합니다. 중요한 건 합친 순서가 곧 규칙이라는 점입니다. 동점이 두 번 나오는데, 이건 구현이 먼저 센 쌍을 고르기 때문에 정해진 것입니다. (3분 · 중심 슬라이드, 화이트보드로 1단계 빈도를 직접 세어 보여 주기)

Byte Fallback: 어휘에 없는 글자는
UTF-8 바이트로 쪼갭니다

모든 글자는 UTF-8로 1–4바이트입니다(영어 1, 한글 음절 3, 이모지 4). 바이트 값은 256가지뿐이라 <0x00>…<0xFF>를 어휘에 넣어 두면 어떤 글자도 표현되고 <unk>가 생기지 않습니다.

대가는 길이입니다. 어휘에 없는 한글 음절 하나가 토큰 3개가 됩니다.

BPE 병합과는 별개 규칙입니다. 병합은 자주 나오는 조각을 만들고, byte fallback은 어휘 밖 글자를 처리합니다.

어휘에 없는 글자는 <unk> 대신 UTF-8 바이트로 쪼갭니다. 바이트 토큰 256개를 어휘에 미리 넣어 두면 어떤 글자도 표현됩니다. 대가는 길이입니다. 한글 음절이 어휘에 없으면 토큰 3개가 됩니다. (W01 덱은 LLaMA 어휘의 한 음절 한글 토큰이 111개라고 보고했습니다. 이 수치는 제가 재현하지 않았으니 “W01 덱에 따르면”이라고 말합니다.) (2분)

장난감 BPE와 실제 tokenizer

1단계는 BPE 원리를 구현해 슬라이드 4와 같은 순서가 나오는지 봅니다. 2단계는 이미 학습된 LLaMA tokenizer를 불러와 실물을 관찰합니다. huggyllama/llama-7b는 LLaMA 1 재배포본이고, Llama 2는 원문상 같은 tokenizer입니다.

1단계 · 장난감 BPE 원리

corpus = {"l o w": 5, "l o w e r": 2,
          "n e w e s t": 6, "w i d e s t": 3}
merges = []
for step in range(4):                # 학습
    pair, freq = pair_counts(corpus).most_common(1)[0]
    merges.append(pair)              # 순서 = 규칙
    corpus = merge(corpus, pair)
def encode(word):                    # 적용
    sym = list(word)
    for a, b in merges:              # 배운 순서대로
        sym = merge_pair(sym, a, b)
    return sym
merges = [('e','s'), ('es','t'), ('l','o'), ('lo','w')]
encode("lowest") → ['low', 'est']

Llama 3는 tokenizer를 바꿨습니다. SentencePiece 대신 OpenAI의 tiktoken 어휘 100K에 비영어 토큰 28K를 더해 128K입니다. 원문은 영어 압축률이 3.17에서 3.94 글자/토큰으로 좋아졌다고 적습니다. 원문이 적지 않은 부분은 직접 돌려 봤습니다. 녕이 한 토큰이 됐고, 숫자는 한 자리씩이 아니라 세 자리까지 묶였습니다. 이건 실행 관찰이지 원문 주장은 아닙니다. (2분) 참고: PyTorchKR 글은 Meta의 “Understanding the Llama 3 Tokenizer | Llama for Developers” 영상을 GPT로 요약한 글이라 원문 확인용으로는 Llama 3 논문 §3.2를 씁니다.

tiktoken이란?
OpenAI의 빠른 BPE tokenizer

OpenAI가 공개한 BPE tokenizer 라이브러리입니다(“a fast BPE tokeniser for use with OpenAI's models”). 자체 벤치마크에서 HF의 GPT-2 tokenizer보다 3–6배 빠릅니다.

Llama 3에 들어간 게 맞습니다. 논문 §3.2가 “tiktoken의 100K 토큰”을 썼다고 적고, Meta의 공식 코드도 tiktoken으로 tokenizer를 불러옵니다.

SentencePiece(Llama 2)와 다른 점
① 정규식으로 단어·숫자(최대 3자리)·구두점 덩어리를 먼저 나누고, 그 안에서만 BPE
I bought 2026 apples! 7 (Llama 2: 10)
② 바이트 단위 BPE: 바이트 256개에서 출발해 byte fallback이 따로 없고, 토큰 경계가 글자 중간에 올 수 있음
냈다EB 8388 + 다 “냈”이 두 토큰에 걸침
Llama 3에 들어간 증거
# meta-llama/llama3 · llama/tokenizer.py (발췌)
import tiktoken
from tiktoken.load import load_tiktoken_bpe
mergeable_ranks = load_tiktoken_bpe(model_path)

근거: openai/tiktoken README · meta-llama/llama3 · tokenizer.py · Llama 3 · §3.2 · Llama 3 playground
tiktoken은 OpenAI가 GPT 모델용으로 공개한 BPE tokenizer 라이브러리입니다. README는 다른 오픈소스 tokenizer보다 3에서 6배 빠르다고 하는데, 이건 OpenAI 자체 벤치마크입니다. Llama 3에 들어간 게 맞습니다. 논문이 tiktoken의 100K 토큰에 비영어 28K를 더했다고 적고, Meta가 공개한 Llama 3 코드도 tiktoken 라이브러리로 tokenizer를 불러옵니다. SentencePiece와 다른 점은 두 가지입니다. 먼저 정규식으로 단어, 숫자, 구두점 덩어리를 나눈 뒤 그 안에서만 병합해서, 숫자가 최대 세 자리로 묶입니다. 그리고 바이트 단위라 byte fallback이 따로 필요 없는 대신, “냈다”처럼 토큰 경계가 글자 중간에 올 수 있습니다. 초고속이라는 건 라이브러리 속도 얘기지 모델 성능과는 별개입니다. (2분)

같은 뜻이어도 한국어는
Llama 2에서 2.5배 길었습니다

같은 내용을 영어·한국어로 쓰고 토큰 수를 셌습니다. Llama 2에서 한국어는 30토큰으로 영어(12)의 2.5배, Llama 3에서는 12 대 11로 거의 같습니다.

playground에 직접 넣어 본 두 문장도 같은 경향입니다. 영어는 Llama 2·3 모두 5토큰인데, 한국어는 9 → 7로 줄었습니다. 두 문장은 번역쌍이 아니라 참고용입니다.

LLaMA가 영어에 강한 이유:
데이터도 영어, 토큰도 영어에 싸다

① 데이터 — 원문이 밝힌 이유입니다. LLaMA 1은 웹(82%)에서 영어가 아닌 페이지를 버렸고, Wikipedia 20개 언어에도 한국어는 없습니다. Llama 2도 영어 89.70%, 한국어 0.06%입니다.

② tokenizer — 같은 내용이 한국어로는 2.5배의 토큰을 씁니다. 이건 원문이 아니라 발표자 해석입니다.

LLaMA 논문만 봐도 영어에 강하다고 하는데, 왜 그런지 두 갈래로 나눠 보겠습니다. 첫째는 데이터입니다. 이건 원문이 직접 말합니다. LLaMA 1은 웹 데이터에서 영어가 아닌 페이지를 버렸고, 위키피디아 20개 언어에도 한국어는 없습니다. Llama 2도 영어가 89.7%이고, 논문 스스로 영어 사용에서 가장 잘 동작하고 다른 언어에서는 성능이 불안정하다고 씁니다. 둘째는 tokenizer입니다. 같은 뜻의 문장이 한국어로는 2.5배 토큰을 쓰니까, 같은 4K context에 담기는 내용이 영어의 40% 정도입니다. 다만 이건 원문 주장이 아니라 제 해석이고, 문장 한 쌍으로 낸 거친 추정입니다. “segmentation 문제”와
“어휘 배분 문제”는 다릅니다

Segmentation은 무엇을 한 단위로 볼지의 문제입니다. 한국어는 띄어쓰기가 있지만 어절 하나에 단어와 조사·어미가 붙는 교착어라, 공백으로만 자르면 “정민이는·정민이가·정민이를”이 모두 다른 단어가 됩니다.

12장의 길이 차이는 주로 어휘 배분 문제입니다. Llama 2 tokenizer는 한국어 병합을 거의 배우지 못했습니다.

① Segmentation · 단위를 어떻게 자를까
어절정민이는 → 형태소정민이는
공백 단위로 자르면 조사·어미가 붙은 어절마다 새 단어가 생깁니다. SentencePiece 논문은 “기존 도구는 입력이 이미 단어로 나뉘었다고 가정한다”고 지적하고, 원문 문장에서 바로 학습하는 방식을 제안했습니다.
② 어휘 배분 · 한국어 조각이 어휘에 얼마나 있나
Llama 2▁정민이는▁바부다. 10
Llama 3정민이는 바부다. 7
Llama 2는 음절이 거의 다 따로입니다. Llama 3는 “이는”을 한 토큰으로 배웠습니다. 자르는 규칙이 아니라 배운 병합의 차이입니다.
질문에 대한 답playground에서 본 차이는 ②가 주원인입니다. ①은 교착어인 한국어의 tokenizer를 설계할 때 처음부터 따라오는 배경 문제입니다.
근거: SentencePiece · Kudo & Richardson 2018 · Abstract · Petrov et al. 2023 · Llama 1·2 playground · Llama 3 playground
playground에서 영어가 훨씬 적게 나온 게 SentencePiece가 말하는 segmentation 문제인지 질문이 있었습니다. 엄밀히는 다른 문제입니다. Segmentation은 무엇을 한 단위로 볼지의 문제이고, 제가 본 길이 차이는 tokenizer가 한국어 조각을 어휘에 얼마나 배정했느냐의 문제입니다. Llama 2는 정, 민, 이, 는이 다 따로인데 Llama 3는 “이는”을 한 토큰으로 배웠습니다. 다만 한국어가 교착어라서 어절과 단어가 다르다는 점은 한국어 tokenizer를 설계할 때 항상 따라오는 문제라서, 다음 장에서 이걸 어떻게 풀어 왔는지 봅니다. (2분)

한국어가 BPE에 약한가?
그냥 쓰면 불리할 뿐입니다

BPE는 “자주 붙어 나오는 쌍”만 봅니다. 이 기준이 한국어와 세 군데에서 어긋납니다.

하지만 같은 BPE라도 형태소를 고려하거나(HyperCLOVA X) 한국어 어휘를 늘리면(Llama 3) 한국어 길이가 크게 줄었습니다.

어긋나는 곳무슨 일이 생기나근거
① 글자 수가 많다한글 음절은 11,172개(영어 알파벳 26개). 글자 단위면 드문 음절이 어휘 밖으로 밀려 byte fallback, 바이트 단위면 음절 하나가 3바이트라 병합을 배워야 겨우 한 글자가 됩니다.유니코드 U+AC00–D7A3 (직접 계산) · HyperCLOVA 2021
② 빈도만 본다형태소 경계를 모른 채 합쳐서, 조각이 형태소를 가로지르거나 지나치게 잘게 쪼개집니다.KLUE 2021 · Lee et al. 2024 (과분절)
③ 데이터가 적으면
병합을 못 배운다		한국어 0.06%로는 “이는” 같은 병합이 생기지 않아 음절이 다 따로 남습니다.Llama 2 Table 10 · 14장

그럼 한국어는 BPE에 약한 걸까요? BPE 자체가 안 맞는다기보다, 그냥 쓰면 세 군데서 불리합니다. 첫째, 한글은 음절이 11,172개나 돼서 글자 단위로는 드문 음절이 어휘 밖으로 밀리고, 바이트 단위로는 음절 하나가 3바이트라 병합을 배워야 겨우 한 글자가 됩니다. 둘째, BPE는 빈도만 보고 합치기 때문에 형태소 경계를 모릅니다. 셋째, 데이터가 적으면 병합 자체를 못 배웁니다. 그런데 같은 BPE를 쓰면서도 HyperCLOVA X나 Llama 3는 한국어를 잘 처리합니다. 그래서 BPE에 취약하다기보다 영어 데이터로 빈도만 보고 학습한 BPE가 불리하다고 보는 게 정확합니다. (2분)

그럼 한국어엔 무엇을?
형태소 + 충분한 어휘

BPE냐 WordPiece냐보다 형태소 경계를 지키는지와 한국어가 어휘에 충분히 들어갔는지가 중요합니다. KLUE 논문은 같은 tokenizer를 BPE·WordPiece 두 이름으로 부를 정도입니다.

그럼 한국어에는 무엇을 써야 할까요? 처음에는 WordPiece를 써야 하나 싶었는데, 찾아보니 알고리즘 이름보다 두 가지가 중요했습니다. 형태소 경계를 지키는지, 그리고 한국어가 어휘에 충분히 들어갔는지입니다. 제가 찾은 2012년 WordPiece 논문은 일본어·한국어 음성 검색에서 데이터로 단위를 배운다는 출발점이지만 형태소를 직접 다루진 않습니다. 형태소로 먼저 나눈 뒤 BPE를 한 방식이 한국어 과제 대부분에서 가장 좋았고, KLUE는 MeCab으로 형태소를 나눈 뒤 subword를 학습했습니다. 네이버 HyperCLOVA X는 형태소를 고려한 byte-level BPE로 한국어 압축률이 가장 좋았고, Llama 3는 비영어 어휘를 늘려 한국어 길이를 크게 줄였습니다. (2분)
