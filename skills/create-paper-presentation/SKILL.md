# 논문 발표자료 만들기

원문의 주장을 발표자가 설명할 수 있는 메시지·도식·비교로 바꾼다. 기존 목차와 파트 구성이 있으면 유지하고, 각 파트의 실제 내용과 검토된 비중에 맞춰 분량을 배정한다. 디자인 참고 자료의 연구 제안용 목차를 논문 정독 자료에 이식하지 않는다.

## 입력과 출력

입력은 논문 판본·출처, 파트 추출 결과, 발표 범위와 담당자 Markdown, 필요한 표·그림·수식의 원문 위치다. 빠진 범위는 확인 가능한 입력으로부터 제안한다. 사람 검토 상태는 별도 기록한다. 사용자가 미검토 자료의 초안을 요청했다면 진행하되, 내용·분담 승인을 받은 것으로 바꾸지 않는다.

출력은 독립 실행 HTML, 원문과 분석 문서 링크, 실제 화면을 다시 읽고 쓴 피드백이다. 생성 파일의 저장 위치는 사용자의 요청과 저장소 규칙을 따른다. 발표자료 생성은 기존 학습목표·공식 주차 문서의 개편이나 게시를 포함하지 않는다.

## 내용에서 화면으로

1. 기존 목차·핵심 메시지·근거를 읽는다. 목차가 없으면 문제 → 설계·방법 → 실험 → 한계·질문을 기본 흐름으로 삼는다. 파트 개수와 장수를 같게 맞추지 않는다.
2. 각 장에 **하나의 설명할 질문, 답이 되는 제목, 이를 뒷받침하는 근거**를 정한다. 파트 추출의 K ID와 원문 위치를 연결한다. 상세 읽기 지도는 근거 저장소로 남기고 그 문장을 그대로 전부 옮기지 않는다.
3. 구성요소는 입력 → 연산/변경 → 출력과 다음 요소의 관계로 설명한다. 블록의 실제 위치, 공유·분기·잔차 경로가 질문의 핵심이면 선과 위치로 드러낸다. 선은 연산·데이터·학습 중 무엇의 흐름인지 명확해야 한다.
4. 수치 비교는 모델·학습 단계·데이터셋·metric·shot·sampling 조건을 같은 화면에 붙인다. 미기술은 미기술로 유지한다. 표의 값과 직접 산출한 차이는 구분한다. 저자 가설, 관찰, 발표자의 해석은 해당 문장 가까이에 표시한다.
5. 설계 선택 장에는 **대안 → 고른 것 → 원문 이유 → 외부 근거**를 둔다. 원문이 이유를 밝히지 않았으면 "미기술"로 적고, 외부 근거에는 그 논문이 인용한 것인지 함께 적는다.
6. 선행 연구 → 이 논문 → 이후를 비교할 때는 같은 축의 숫자 하나로 꿴다(예: 파라미터당 토큰 1.7 → 20 → 21 · 149).
7. 본편에는 "무엇을 골랐고 결과가 무엇인가"만 둔다. 원문이 한 줄이나 출처 표기로 넘어간 배경 개념, 유도, 대안 비교는 부록 Background로 보낸다. 부록 첫 장에는 주제 · 원문이 한 말 · 부록에서 볼 것 · 다음 주 담당 파트를 표로 두고, 주제별 로드맵을 그 뒤에 몰아 둔다. 본편의 해당 장에는 "다음 주 깊게 다시 다룰 내용" 표시를 붙인다.
8. 정보에 맞는 배치를 고른다. 절차에는 흐름도, 구조 변경에는 전후 블록, 같은 단위의 비교에는 정량 차트, 설정 조회에는 표가 적합하다. 전체 흐름·도식 중심·비교·참조 배치를 섞되, 기존 순서는 보존한다. 박스의 수나 장식의 양을 품질 기준으로 삼지 않는다.

화면에 넣는 비율 · 속도 · 점수와 "누가 무엇을 인용했나"는 원문을 다시 열어 확인한다. 토크나이저 · 설정 파일처럼 직접 돌릴 수 있는 것은 돌린 결과를 쓴다. 분류를 세우면 반례를 먼저 찾는다.

시각화·근거의 구체 기준은 [design-and-evidence.md](references/design-and-evidence.md)를 사용한다.

## 명확하게: 중간 과정을 생략하지 않는다

발표자는 장만 보고 설명해야 한다. 만든 사람이 이해한 것을 전제로 쓰지 않는다.

- **단계를 건너뛰지 않는다.** 입력 → 중간 결과 → 출력을 실제 값으로 모두 보인다. 예: 글자 → 유니코드 번호 → UTF-8 바이트 → 합치기 한 번씩 → token_id. 문서 → 단어 묶음 → 해시별 최솟값 → 서명 → 띠 → 칸 → 후보.
- **용어 · 약어는 처음 나오는 장에서 푼다.** 예: LSH(Locality-Sensitive Hashing). 원문에 없는 개념을 설명용으로 들이면 그렇게 적는다(예: Jaccard는 원문에 없고 MinHash가 추정하는 값).
- **숫자에는 이름을 붙인다.** 같은 숫자가 두 의미면 둘 다 적는다(예: 합치기 순위 = 결과 토큰의 token_id). 축 · 비율은 분자 · 분모와 '높을수록/낮을수록'을 적고, 그림을 직접 확대해 방향을 확인한다.
- **예시 하나를 이어서 쓴다.** 앞뒤 장이 같은 예시 · 같은 숫자로 이어지게 한다. 예시는 메시지를 실제로 보여 주는 것으로 고른다(새로 추가된 규칙을 설명하면서 전부 기존 규칙인 예시를 쓰지 않는다).
- **'A와 B는 다르다' 장은 같은 입력으로 양쪽을 나란히** 보인다. 정의 비교표만 두지 않는다.
- **비슷해 보이는 두 장은 제목에서 역할을 나눈다**(무엇을 하는가 / 어떻게 정하는가).
- 다음 질문이 나올 자리(왜 두 개씩만? 순서대로 묶나, 비슷한 걸 찾나?)를 미리 장 안에서 답한다.

## 원문 그림 · 표를 먼저 넣는다

- 실험 결과 · 예시 · 구조를 설명하는 장은 **논문의 Figure · Table 원본을 잘라 넣는 것이 기본**이다. 직접 만든 표는 원본을 보조할 때만 쓴다. 값을 그림에서 눈으로 읽었다면 그 그림을 같은 장에 넣고 "그림에서 읽은 값"이라고 적는다.
- 장을 쓰기 전에 그 절의 Figure · Table 목록을 PDF에서 확인하고(본문 검색 `Figure N:` · `Table N:`), 쓸 것과 안 쓸 것을 정한다. 원문 예시 그림(트리 · 프롬프트 · 사례)이 있으면 그 예시를 한 단계씩 풀어 쓰는 장을 따로 둔다.
- 자른 이미지는 직접 열어 위아래 여백 · 잘린 캡션이 없는지 확인한다.

## 표의 줄과 숫자

- **표의 모든 줄은 같은 열을 채울 수 있는 비교 대상이어야 한다.** 핵심 열(점수)이 '—'인 줄은 넣지 않는다. 예: 데이터 풀은 학습 결과가 없으니 줄이 아니라 캡션으로 적고, 비교는 같은 크기 · 같은 조건의 기준선(무작위 표본 등)으로 한다.
- 점수 · 승률은 **무엇 대비인지**(예: text-davinci-003 대비 승률), 차이가 %인지 %p인지 원문 표 캡션에서 확인한다.
- 같은 열은 같은 단위로 적는다(한 줄은 개수, 한 줄은 비율로 섞지 않는다). 개수 · 규칙 수처럼 다른 것을 센 숫자는 같은 모양으로 나란히 두지 않는다.
- 모델 크기 등은 모든 줄에서 같은 순서(작은 것 → 큰 것)로 적는다.

## HTML 제작

[deck-shell.html](assets/deck-shell.html)은 밝은 테마, 가로 이동, 목차, 키보드, 읽기 모드, 인쇄를 갖춘 시작점이다. 단일 파일 안에 CSS·JS·코드로 그린 도식을 포함한다. 원문 이미지가 핵심 증거라면 판독 가능한 크기로 인용하고, 자체 도식은 설명용 재구성임을 표시한다.

반복 제작에는 다음 도구를 사용할 수 있다. JSON 형식과 실행 가능한 작은 예시는 [example-slides.json](assets/example-slides.json)에 있다. `body`·`visual`은 작성자가 검토한 HTML 조각이다.

```sh
python3 scripts/build_deck.py assets/example-slides.json /tmp/paper-example.html
node scripts/check_deck.cjs /tmp/paper-example.html /tmp/paper-example-check
```

대본은 장 제목을 키로 하는 Markdown(`script.md`)을 원본으로 두고, 빌드 전에 제목이 맞는 장의 `note`로 옮긴다. shell은 `N` 키와 오른쪽 아래 버튼으로 현재 장의 대본을 띄운다. 대본은 발표자와 장마다 같이 다듬고, 원문 미기술 · 발표자 해석은 대본에서도 그렇게 말한다.

검사기는 Playwright를 사용한다. 기본 모듈 탐색이 안 되면 `PLAYWRIGHT_MODULE`에 설치된 모듈 경로, 필요한 경우 `CHROME_PATH`에 브라우저 실행 경로를 지정한다. 의존성이 없으면 가능한 브라우저 도구로 같은 검사를 수행하고 미수행 항목을 기록한다.

## 실제로 보고 수정하기

전체 슬라이드를 렌더해 흐름·반복·밀도를 보고, 가장 복잡한 도식·표·수식은 원래 크기로 읽는다. 데스크톱, 사용 중인 패널 크기, 휴대폰에서 확인한다. 넘침 검사는 자동화하되 실제로 읽히는지는 화면으로 판단한다. 작은 글자를 더 줄여서 해결하기보다 장을 나누거나 읽기 모드를 제공한다. 한 장에 메시지가 둘 이상이면 먼저 나눈다.

휴대폰과 높이가 낮은 화면에서는 한 장씩 표시하는 읽기 모드를 사용하고, 고정 크기 슬라이드로 축소하는 전환은 숨긴다. 다음 장은 맨 위에서 시작하며, 가로로 넘치는 표·도식에 포커스가 있으면 방향키를 해당 영역의 스크롤에 사용한다.

표본 수치를 원문과 다시 대조하고, 화살표 연결·축·범례·출처 링크·이동·터치 스크롤을 확인한다. 피드백은 **관찰한 문제 → 실제 수정 → 확인 근거 → 남은 한계**로 적는다. 디자인 개선을 요청받았다면 피드백만 제안하고 멈추지 말고 해당 장을 고친 뒤 다시 본다. 자동 검증과 AI 검토는 사람 승인과 구분한다.
