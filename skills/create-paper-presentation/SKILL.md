# 논문 발표자료 만들기

원문의 주장을 발표자가 설명할 수 있는 메시지 · 도식 · 비교로 바꾼다. 목표는 **발표 화면은 가볍게 읽히고, 근거를 펼치면 검증되는 덱**이다. 근거와 원문 그림 · 표는 지우지 않고, 한 화면에 동시에 보이는 양을 줄인다. 기존 목차와 파트 구성은 유지하고, 디자인 참고 자료의 연구 제안용 목차를 이식하지 않는다.

## 입력과 출력

입력은 논문 판본 · 출처, 읽기 지도, 발표 범위와 담당자 Markdown, 표 · 그림 · 수식의 원문 위치, **발표 시간(분)**이다. 발표 시간을 모르면 묻고, 답이 없으면 25분으로 두고 그 가정을 기록한다. 읽기 지도에 '발표 시간과 장 배분'이 있으면 거기서 시작한다. 사람 검토 상태는 따로 기록하고, 미검토 자료로 초안을 만들어도 승인받은 것으로 바꾸지 않는다.

출력은 독립 실행 HTML과 그 원본(덱 JSON · 근거 원장 `claims.json` · 대본 `script.md`), 원문 · 분석 문서 링크, 검사 보고, 실제 화면을 보고 쓴 피드백이다. 저장 위치는 사용자 요청과 저장소 규칙을 따르고(이 저장소는 `docs/weeks/README.md`의 주차 폴더 구성: 덱은 `slides/`), 학습목표 · 공식 주차 문서를 고치거나 게시하지 않는다. 읽기 지도는 저장소에 올리지 않는 작업 파일이므로 덱에서 링크하지 않는다. 출처 링크는 원문(arXiv · 공식 문서)에 걸고, 읽기 지도 항목은 `ids` 라벨로만 남긴다.

## 네 층

정보를 **화면**(결론 · 주 시각 · 결론을 바꾸는 조건 · 짧은 출처 줄), **대본**(설명 순서), **근거 패널**(장마다 E 키로 펼침), **부록**(증명 · 다른 조건 재계산 · 원문 표 전체)에 나누고, 네 층 모두 같은 근거 원장을 다른 밀도로 쓴다.

- 화면에는 **없으면 결론이나 그림을 오해하게 되는 정보**만 둔다: 결론, 핵심 기제, 결론을 바꾸는 조건, 계산의 일반식, 설계 선택의 원문 이유 한 문장, 근거가 된 원문 그림 · 표.
- 결론을 바꾸는 조건을 대본 · 패널에만 숨기지 않고, 주장에 필요한 정보를 부록에만 두지 않는다.
- 출처 줄은 모든 장의 화면에 보인다. 화면엔 식별자(예: `Llama 2 Table 1 (p.6)`), 전체 출처는 패널.
- 단계는 생략하지 않고 층을 나눈다. 장 하나(패널 포함)만 보고 따라갈 수 있어야 한다.

정보별 자리 · 밀도 · 시간 예산 · 재배치 예는 [screen-budget.md](references/screen-budget.md), 원장은 [claim-ledger.md](references/claim-ledger.md).

## 작업 순서

1. **읽기.** 읽기 지도 · 배정 범위 · 학습목표 · 기존 목차. 목차가 없으면 문제 → 설계 · 방법 → 실험 → 한계 · 질문.
2. **근거 원장.** 쓸 숫자와 주장을 원자적 주장 하나씩 `claims.json`에 적고, 원문 사실과 계산 가정(층 · head 수 · dtype · 단위 · cache 정의)을 먼저 대조한다. 표지를 붙였다고 계산이 맞아지지 않는다.
3. **장 설계.** 한 장 = 원자적 주장 하나 또는 인과 사슬 하나(예: GQA → KV head 감소 → KV cache 감소). 장마다 `kind`와 설명 시간을 정해 예산에 맞추고, 본편 끝에 열린 질문 · 토론 장을 둔다.
4. **장 쓰기.** 화면 · 대본 · 근거 패널을 함께 쓴다.
5. **빌드.** `build_deck.py … --script … --lint`, lint 경고를 고친다.
6. **렌더 검사.** `check_deck.cjs`로 재고 화면을 직접 본다.
7. **근거 손실 확인.** 기준선(새 덱은 원장 + 읽기 지도의 '계산해 보면', 개정은 이전 빌드의 coverage)과 비교해 출처 연결 · 계산 재현 · 조건 유지를 보고, 잃은 것은 되살린다.

## 장 하나

- **결론 1(제목) + 주 시각 1 + 핵심 조건 0–1.** 조건이 없으면 조건 줄을 만들지 않고, 빈자리를 다른 설명으로 채우지 않는다.
- **역할을 나눈다.** 제목 = 무엇이 달라졌나, 주 시각 = 왜 · 어떻게, 조건 줄 = 언제 성립하나, 대본 = 어떻게 설명하나. 제목 · 본문 · 그림 · 캡션이 같은 말을 반복하지 않는다.
- **본문 설명은 0–2문장.** 글자를 줄이기 전에 같은 정보를 말하는 문단 · 식 · 시각 · 캡션을 하나로 합친다. 글자 수 · AU · 높이 · 주 시각 면적 목표는 screen-budget.md 3–4절.
- **주 시각은 핵심 기제를 가장 직접 보여 주는 것**(`data-main`). 곱 · 합으로 된 정량 결과는 요인 분해를 주 시각으로 두고, 변하지 않은 항목은 '동일' 표지로 남긴다. 분해 값은 실제 config · 식과 맞아야 한다.
- **근거 표지**(`.ev-chip`)는 그 종류가 해당하는 **모든 장**에 붙인다. 덱에서 한 번만 쓰는 것은 풀이('왜 추정인가')다. 논문 값과 발표자 계산값이 한 화면에 있으면 반드시 구분한다. 라벨 · 근거 범위 · 위계는 [design-and-evidence.md](references/design-and-evidence.md) '근거 표지 위계'.
- **대본은 화면의 복사본이 아니다.** 발표할 말만 쓰고, 결과 장에는 토론 질문 하나를 넣는다. 제작 · 검토 메모는 검토 기록에.
- 제목 · 비교 짝 · 첫 등장 정의 · 같은 조건 비교는 design-and-evidence.md.

## 내용에서 화면으로

1. 각 장에 **설명할 질문 하나, 답이 되는 제목, 근거**를 정하고 읽기 지도 항목(파트 · RQ 번호 · 개념 페이지 이름) · claim id · 원문 위치를 잇는다. 장 `ids`에는 그 읽기 지도 항목의 라벨을 쓴다. 읽기 지도 문장을 그대로 옮기지 않는다.
2. 구성요소는 입력 → 연산/변경 → 출력으로 설명한다. 공유 · 분기 · 잔차 경로가 핵심이면 선과 위치로 보이고, 선이 무엇(연산 · 데이터 · 학습)의 흐름인지 밝힌다.
3. 수치 비교에는 모델 · 단계 · 데이터셋 · metric · shot · sampling 조건을 붙인다(결론을 바꾸는 것은 화면, 나머지는 패널). 미기술은 미기술로 두고, 저자 가설 · 관찰 · 발표자 해석은 그 문장 가까이에 표시한다.
4. 설계 선택 장: **대안 → 고른 것 → 원문 이유 → 외부 근거.** **원문 이유는 화면에 한 문장(풀어 쓴 말 + 출처 식별자)으로, 원문 그대로의 인용은 패널에** 둔다. 이유가 없으면 "미기술", 외부 근거는 그 논문이 인용했는지 함께 적는다.
5. 선행 연구 → 이 논문 → 이후는 같은 축의 숫자 하나로 꿴다(예: 파라미터당 토큰 1.7 → 20 → 21 · 149).
6. **배정 항목의 기제 · 유도는 본편에.** 왜 · 어떻게에 답하는 단계는 본편(넘치면 장을 나눔)에 두고 마지막 줄에 원래 질문의 답을 쓴다. 단계 안의 대수와 숫자 대입은 패널, 증명 · 다른 크기/조건 재계산 · 원문 표 전체 · 배정 밖 배경은 부록. 예산을 넘을 때의 우선순위는 screen-budget.md 6절.
7. **평가 절은 Table마다 개요 장부터.** 주장형 제목 + 주장 주석 표(HTML 표 · 범례 · 판정 띠). 표에 대한 저자 주장은 판정 띠의 줄로 옮긴다('저자:' 주어, 예외는 같은 줄, 결과 칸에 차이값). 세부는 screen-budget.md 7절.
8. 배치는 정보에 맞춘다(절차 = 흐름도, 구조 변경 = 전후 비교 쌍, 곱 = 요인 분해, 같은 단위 비교 = 차트, 설정 = 표). 박스 수나 장식은 품질 기준이 아니다.

화면의 비율 · 점수와 "누가 무엇을 인용했나"는 원문을 다시 열어 확인하고, 직접 돌릴 수 있는 것(토크나이저 · 설정 파일)은 돌린 결과를 쓴다. 분류를 세우면 반례를 먼저 찾는다.

## 명확하게: 중간 과정을 생략하지 않는다

발표자는 장만 보고 설명해야 한다. 만든 사람이 이해한 것을 전제로 쓰지 않는다.

- **단계를 건너뛰지 않는다.** 입력 → 중간 결과 → 출력을 실제 값으로 모두 보인다. running example의 실제 값 사슬은 값이 적힌 단계 카드로 **화면**에 둔다. 패널로 보내는 것은 식에 숫자를 넣는 산술(`p.subst`)과 긴 대입뿐이다. 예: 글자 → 유니코드 번호 → UTF-8 바이트 → 합치기 한 번씩 → token_id. 문서 → 단어 묶음 → 해시별 최솟값 → 서명 → 띠 → 칸 → 후보.
- **용어 · 약어 · 기호는 처음 나오는 장에서 `<dfn>`으로 푼다**(예: LSH(Locality-Sensitive Hashing)). 원문에 없는 개념을 설명용으로 들이면 그렇게 적는다(예: Jaccard는 원문에 없고 MinHash가 추정하는 값).
- **숫자에는 이름을 붙인다.** 같은 숫자가 두 의미면 둘 다 적는다(예: 합치기 순위 = token_id). 축 · 비율은 분자 · 분모와 '높을수록/낮을수록'을 적고, 그림을 확대해 방향을 확인한다.
- **예시 하나를 이어서 쓴다.** 앞뒤 장이 같은 예시 · 같은 숫자로 이어지고, 예시는 메시지를 실제로 보여 주는 것으로 고른다.
- **'A와 B는 다르다' 장은 같은 입력으로 양쪽을 나란히.** 정의 비교표만 두지 않고, 조건이 다른 두 대상을 '같아도'로 묶지 않는다.
- **비슷해 보이는 두 장은 제목에서 역할을 나눈다**(무엇을 하는가 / 어떻게 정하는가).
- 다음 질문(왜 두 개씩만? 순서대로 묶나, 비슷한 걸 찾나?)을 장 안(화면 · 패널 · 대본)에서 미리 답한다.

## 원문 그림 · 표를 먼저 넣는다

- 장을 쓰기 전에 그 절의 Figure · Table 목록을 PDF에서 확인하고(`Figure N:` · `Table N:` 검색) 쓸 것을 정한다. 원문 예시 그림(트리 · 프롬프트 · 사례)은 한 단계씩 풀어 쓰는 장을 따로 둔다.
- **주장이 원문 Figure · Table에 기대는 장에는 원본이 화면에 있다.** 자리는 둘 중 하나다.
  - **주 시각**: 장의 주제가 원문 자체(예시 그림 따라가기, 모양이 곧 주장인 그래프)이거나, 필요한 칸만 잘라 화면에서 글자가 읽힐 때(C-CROP-GLYPH).
  - **썸네일**: HTML로 다시 그린 것(주장 주석 표 · 요인 분해 · 도식)이 주 시각일 때 그 옆에 작게(AU 0, 눌러서 확대).
  - 어느 쪽이든 근거 패널에 전체 크기 crop을 둔다. 마크업은 [shell-components.md](references/shell-components.md) '원문 crop'.
- 다시 그린 표 · 도식에는 '원문 · 쪽 · 포함 · 생략 · 발표자 표시' 캡션을 단다. 셀 값 · 머리글 · 단위 · shot · 각주 · 비교 기준은 원문 그대로, 원문 굵게와 발표자 강조는 범례로 구분, 본문과 표가 다르면 각주. 자체 도식은 설명용 재구성임을 표시한다.
- 그림에서 눈으로 읽은 값은 그 그림을 같은 장에 두고 "그림에서 읽은 값"이라고 적는다.
- 자른 이미지는 직접 열어 여백 · 잘린 캡션을 확인한다. 같은 원본이 여러 장에 필요하면 주장의 근거로 쓰는 첫 장의 화면에 두고, 값만 빌리는 장은 패널에서 그 장으로 링크(`[[@key]]`)한다.

HTML판만 읽은 경우의 출처 · 캡처 표기와 표의 줄 · 숫자 규칙(비교할 수 있는 줄만, '무엇 대비', 같은 열 같은 단위)은 design-and-evidence.md '출처 라벨' · '표의 줄과 숫자'.

## HTML 제작

[deck-shell.html](assets/deck-shell.html)은 단일 파일 시작점이다. 덱 JSON에 `"shell_version": 2`를 두면 근거 패널(E) · 대본(N) · 전체화면(F) · 상호참조 · crop 확대 · 수식 사전 렌더가 켜지고, 없으면 출력은 예전(v1)과 같다. 필드 · 대본 병합 · 수식 · 상호참조 · lint · 검사 코드는 [deck-json.md](references/deck-json.md), 부품은 shell-components.md, 예시는 [example-slides.json](assets/example-slides.json) · [example-claims.json](assets/example-claims.json) · [example-script.md](assets/example-script.md). `body` · `visual` · `evidence`는 작성자가 검토한 HTML 조각이다.

```sh
python3 scripts/build_deck.py assets/example-slides.json /tmp/paper-example.html \
  --script assets/example-script.md --lint
node scripts/check_deck.cjs /tmp/paper-example.html /tmp/paper-example-check
```

같은 JSON · 원장 · 대본이면 바이트까지 같은 HTML이 나와야 한다. 고친 뒤 두 번 빌드해 비교한다. 검사기는 Playwright를 쓰고(`PLAYWRIGHT_MODULE` · `CHROME_PATH`), 수식은 `KATEX_MODULE` · `NODE_BIN`으로 찾는다. 의존성이 없으면 가능한 브라우저 도구로 같은 검사를 하고 미수행 항목을 기록한다.

## 실제로 보고 수정하기

전체 슬라이드를 렌더해 흐름 · 반복 · 밀도를 보고, 가장 복잡한 도식 · 표 · 수식은 원래 크기로 읽는다. 장마다 잠깐 보고 결론과 조건을 말할 수 있는지 확인하고(screen-budget.md 11절), 못 하면 글을 더하지 말고 제목이나 주 시각을 고친다. 데스크톱 · 프로젝터 · 전체화면 · 휴대폰(읽기 모드)에서 본다. 글자를 더 줄이기보다 장을 나누거나 층을 옮긴다.

표본 수치를 원문과 다시 대조하고 연결선 · 축 · 범례 · 링크 · 패널 · 확대 · 대본 · 수식 잘림을 확인한다. 근거 보존 · 읽기 쉬움 · 발표자 편의는 따로 본다. 피드백은 **관찰한 문제 → 실제 수정 → 확인 근거 → 남은 한계**로 적는다. 디자인 개선을 요청받았다면 제안에서 멈추지 말고 고친 뒤 다시 본다. 자동 검증과 AI 검토는 사람 승인과 구분한다.
